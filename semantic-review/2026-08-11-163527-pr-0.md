# Internal per-app firewall enforcement and connection history

This change replaces the bundled NetGuard path with an internal per-app VPN firewall, policy/rule editing, and destination history. The prior blockers are mostly addressed: shared-UID apps are visibly ineligible and stripped on save, only eligible selected apps enter the VPN, deselection deletes rules, blocked DNS is recorded without an IP, and quick block uses `DOMAIN_EXACT`. Unknown attribution fails closed under enforcing policies, but malformed DNS bypasses that check, and empty activation can still leave stale enabled state because the service races the settings save. Watch for: **confirmed** stale enabled state after an empty activation; **confirmed** malformed DNS bypass of unknown-UID fail-closed enforcement; **confirmed** retention retry replaying already-written history batches.

**Verdict**: NEEDS_CHANGES

## High-level view

The VPN interface is scoped with `addAllowedApplication` to eligible selected packages, so unselected applications stay outside the tunnel. Shared-UID packages are marked ineligible and filtered again at persistence; deselection also removes their stored rules.

Rule evaluation blocks unattributed flows whenever any enabled selected policy enforces a blocklist or allowlist. DNS normalization has a separate invalid-name branch that returns allow before attribution enforcement, leaving one fail-open path.

Explicit empty activation clears only this app's Always-On ownership and firewall state, while `ACTION_NETWORK_CHANGED` skips that cleanup for NetFree. Cleanup is asynchronous with the settings screen's subsequent write of `true`, so final persisted state depends on scheduling.

Connection history uses a bounded recorder with batched writes, retries, and startup retention. Write and purge are retried as one operation, so a purge-only failure replays a successful write; a failed startup purge has no independent retry until traffic arrives.

1. **Empty-activation settings race — confirmed** — `applyPolicy()` starts the service before `SettingsViewModel` persists `true`; if empty-policy cleanup writes `false` first, the settings save restores stale enabled state. Persist activation before service startup or make activation/cleanup use a generation-aware single owner.
2. **Malformed DNS attribution bypass — confirmed** — an un-normalizable DNS name is explicitly allowed without unknown-UID enforcement. Apply attribution fail-closed before or within the invalid-name branch whenever an enforcing policy exists.
3. **History purge retries duplicate successful writes — confirmed** — `recordBatch()` and `purgeIfDue()` share one retry block, so purge failure repeats an already-committed aggregate increment. Retry writes and retention independently, and schedule startup-purge retries even without incoming events.
4. **Targeted firewall regressions are untested — confirmed** — no tests cover shared UID filtering, attribution fail-closed behavior, empty activation ownership, DNS history, deselection cleanup, recorder failures, or quick-block rule type. Add focused tests around these security and lifecycle boundaries.

<summary>Details</summary>

## Empty activation still races persisted feature state

`SettingsViewModel.saveChanges()` invokes `BlockInternetVpnFeature.applyPolicy()` and only then stores the requested state. Enabling starts `BlockerVpnService`; with no eligible package, the service clears its Always-On ownership and writes `false`. Cleanup can complete before the settings coroutine writes `true`, leaving boot-time/UI state enabled with no VPN. This is **confirmed** at `SettingsViewModel.kt:241-242` and `BlockerVpnService.kt:113-116,177-190`.

The ownership guard limits cleanup to this VPN owner, and `ACTION_NETWORK_CHANGED` passes `deactivateIfEmpty = false`, so NetFree-triggered rebuilds do not directly clear Always-On or internal-firewall state. The race remains on explicit activation/rebuild commands.

## Invalid DNS names bypass unknown-attribution enforcement

Ordinary flows and normalized DNS queries call `evaluateWithAttribution`, which blocks negative or package-less UIDs whenever any enabled `BLOCKLIST` or `ALLOWLIST` policy exists. `onQuery()` instead maps normalization failure directly to `FirewallDecision(blocked = false, reason = "INVALID_DNS_NAME")`. An unknown UID can therefore send a malformed query through the default DNS transport despite an enforcing policy. This **confirmed** fail-open branch is at `FirestackEngineAdapter.kt:152-155`.

## Retention failure can inflate connection counts

The recorder survives Room exceptions and invokes retention at startup, but its retry wraps `repository.recordBatch(batch)` and `purgeIfDue()` together. If the batch transaction commits and retention fails, each retry reapplies the batch, increasing aggregates up to three times before logging it as dropped. This is **confirmed** at `ConnectionHistoryRecorder.kt:50-54`.

A failed startup purge resets its due timestamp but has no timer-based retry; it runs again only after a later event batch, where it is coupled to the duplicate-write behavior. Separate retry loops would preserve counts and make startup retention independent of subsequent traffic.

## Security-sensitive regressions lack focused tests

`:app:compileDebugKotlin` and `:app:testDebugUnitTest` pass, but repository searches found no firewall/history tests for the requested behaviors. This **confirmed** coverage gap leaves UID attribution, ownership cleanup, Room failure recovery, DNS metadata, deselection, and quick-block semantics dependent on manual verification.
