# Per-app internal VPN firewall with local destination history

This change replaces the bundled NetGuard path with an in-process Firestack VPN, per-package policies, Room-backed destination history, quick blocking, and a new firewall configuration screen. It removes NetGuard’s APK/features without uninstalling existing copies, keeps NoPhone packaged, and excludes the shared Room database from backup and device transfer. Package eligibility and attribution can silently bypass enforcement, and the asynchronous history pipeline can stop permanently after one storage error. **Watch for:** **High, confirmed** shared-UID selections are silently omitted from the VPN; **High, confirmed** zero eligible apps leave Always-On pointing at a stopped service while the UI reports the feature active; **High, confirmed** one Room exception permanently kills history recording; **High, likely** unresolved/isolated UIDs take the explicit allow path.

**Verdict**: NEEDS_CHANGES

## High-level view

The VPN interface uses Android’s allowed-application list and delegates forwarding decisions to an atomic `FirewallRuleSnapshot`. Rule-only edits reload the snapshot without replacing the interface, while package selection changes rebuild it. The current eligibility and attribution behavior extends the intended fail-open posture to apps the administrator explicitly selected, without surfacing that protection was skipped.

Firestack flow callbacks evaluate package-scoped domain/IP/port rules and emit bounded asynchronous history events. DNS query decisions use the same evaluator, but blocked DNS names are not emitted into destination history, and a Room write/purge exception terminates the singleton recorder worker rather than degrading and retrying.

Room v3 adds policy, rule, and aggregate history tables through sequential 1→2→3 migrations. Retention only runs after a successful incoming batch, and no migration/aggregation tests exercise upgrade compatibility or cap/age behavior.

The settings UI stages package/mode/transport changes and supports one-click blocking from history. Deselecting an app leaves its rules in the database and in the “active rules” list, while quick block silently converts one observed hostname into a suffix rule covering every subdomain.

<details><summary>Details</summary>

## Selected shared-UID apps never enter the VPN

**High, confirmed:** `BlockerVpnService.eligiblePackages` drops any selected package whose UID maps to more than one package. `FirewallViewModel.loadApps` still offers those packages, `saveSelection` persists them, and the success message says the VPN was rebuilt; no state is returned to the UI to say the selected app was skipped. Because `Builder.addAllowedApplication` is never called for it, all of that app’s traffic remains outside the VPN and bypasses monitoring, allowlists, blocklists, QUIC/DoT options, and history.

This is a release blocker for managed/system apps that use `sharedUserId`. Treat the UID as the enforceable identity and require a single policy for all packages sharing it, or reject/disable the selection before saving with a visible explanation.

## Unknown attribution is an explicit allow decision

**High, likely:** `RuleEvaluator.evaluate` returns `NO_SELECTED_POLICY` with `blocked = false` whenever `FirestackEngineAdapter.packagesForUid` cannot map the callback UID to an enabled policy. `resolveOwnerUid` can only recover a missing UID through `getConnectionOwnerUid` on Android 10+, and isolated-process or stale/unknown UIDs can still produce an empty package set. Those flows are inside a selected-app VPN interface but are forwarded through `Base`, so attribution loss becomes a policy bypass, including for apps configured as allowlist.

The release needs an explicit unknown-attribution policy. A conservative block for enforcement modes, a UID-level mapping established when building the interface, or a clearly constrained supported-API/process model would avoid treating metadata failure as authorization.

## Empty eligibility leaves a false Always-On state

**High, confirmed:** `BlockInternetVpnFeature.applyPolicy` assigns this package as Always-On before the service verifies any eligible selected packages. `BlockerVpnService.rebuildVpn` calls `stopSelf()` when the eligible set is empty, but it does not clear the Always-On owner or update the persisted feature state; `isPolicyActive` then continues to report active solely because the owner package matches. This occurs with no selection and when every selection was removed as shared-UID/ineligible.

The feature should validate eligibility before claiming success, or clear/deactivate ownership when no interface can be established. The UI also needs service/interface status rather than equating DevicePolicyManager ownership with an operating firewall.

## One Room failure permanently disables recording

**High, confirmed:** the only consumer launched by `ConnectionHistoryRecorder.init` calls `repository.recordBatch(batch)` and `purgeIfDue()` without a per-iteration exception boundary. Any SQLite exception, migration/open failure, disk-full condition, or purge failure terminates that coroutine. The channel remains alive, so packet callbacks continue to enqueue and eventually drop events with no consumer and no signal that history has stopped.

Catch and report failures around each batch, retry with bounded backoff, and keep the consumer loop alive. A dropped-event/error counter would also make the bounded `DROP_OLDEST` behavior observable.

## DNS blocks are absent from destination history

**Medium, confirmed:** `FirestackEngineAdapter.FirewallBridge.onQuery` evaluates and routes a blocked query to `BlockAll`, but only writes a file log. `recordConnection` is called from `flow`, requires a destination IP and port, and cannot represent a DNS name rejected before an upstream answer. The history therefore cannot reliably show the blocked domain decision that prevented the connection.

Emit a DNS-specific `ConnectionEvent` directly from `onQuery`, or extend the history model so IP/port can be absent for DNS decisions, using the same package attribution and blocked reason as the decision.

## Retention depends on future successful traffic

**Medium, confirmed:** seven-day deletion and the 10,000-row cap run only after `recordBatch` succeeds, and at most once per process-local 24-hour interval. A quiet device never purges expired records, and the first write failure prevents both recording and retention for the rest of the process. Schedule retention independently at database/application startup or with durable periodic work, while retaining the post-batch cap as a safety net.

## Deselection preserves and relabels old rules as active

**Medium, confirmed:** `FirewallDao.replaceSelectedPackages` deletes deselected policies but not their `firewall_rule` rows. `observeEnabledRules` has no policy join, so `FirewallViewModel` continues to render those rows under “active rules”; reselecting the package silently reactivates them. Either cascade/delete rules on deselection, persist a disabled policy when configuration should be retained, or present archived rules explicitly and require confirmation before reactivation.

## Quick block expands one hostname to an entire suffix

**Medium, confirmed:** `FirewallViewModel.quickBlock` turns any observed domain into `DOMAIN_SUFFIX`. Blocking `api.example.com` therefore also blocks every future subdomain below that name, although the action and success message describe blocking the observed destination. Default to `DOMAIN_EXACT`, or show the rule scope and require an explicit choice before creating a suffix rule.

## Android 5.1 support is removed for the whole application

**Medium, confirmed:** `app/build.gradle.kts` raises `minSdk` from 22 to 23 even though the firewall feature itself is gated at API 24. Existing API 22 installations can no longer update to this release. Confirm that dropping Android 5.1 is deliberate; otherwise isolate/override the engine’s minimum requirement while keeping the application’s existing floor.

## Upgrade and enforcement paths have no targeted tests

**Medium, confirmed:** no unit/instrumentation tests reference the v1→2→3 migrations, history aggregation/retention, `RuleEvaluator`, package eligibility, recorder recovery, DNS decisions, quick block, or reload/rebuild generation behavior. `:app:compileDebugKotlin` succeeds. `:app:testDebugUnitTest` could not complete because the local Android 34 `JdkImageTransform` failed in `jlink`, so the existing suite provided no additional coverage.

Add Room migration tests from v1 and v2, transactional aggregate/cap tests, evaluator precedence and unknown-attribution tests, recorder failure recovery, shared-UID eligibility behavior, and service tests distinguishing snapshot reload from interface rebuild.
