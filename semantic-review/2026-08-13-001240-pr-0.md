# Signed installed-app mini-store with isolated public distribution

This change adds a Device Owner-only mini-store that discovers installed non-system apps, verifies an Ed25519-signed catalog from Cloudflare Pages, downloads immutable APK objects from R2, and updates or removes packages through `PackageInstaller`. APK acceptance is bound to package, newer version, byte size, SHA-256, current signer, and signing lineage; A Bloq remains on its separate GitHub self-update path and is excluded from the catalog. Uninstall protection covers A Bloq, system apps, active admins, the current home/dialer, and kiosk packages, while firewall rules remain package-keyed. **Watch for:** **confirmed** API-33-only package calls make the mini-store unusable below Android 13 despite `minSdk = 23`; **confirmed** package removal between the last installed check and commit converts an update into a new install; **confirmed** update authority never expires after entry authentication; **confirmed** refresh and backup-restore paths weaken catalog rollback protection.

**Verdict**: NEEDS_CHANGES

## High-level view

The catalog trust boundary is separated from hosting: the app embeds the signing public key, verifies a domain-separated payload, and accepts APK URLs only under a package/version/hash-bound R2 prefix. Public GitLab, Cloudflare, or R2 compromise cannot mint a new accepted catalog or APK without the offline private key. A Bloq self-update remains on GitHub and `com.secureguard.mdm` is rejected by both catalog tooling and the client.

The APK file is verified before archive parsing, then package, version, catalog signer, and Android signing lineage are checked against the installed app. The **confirmed** TOCTOU gap is the installed package itself: it can disappear after the final check and before a full-install session commits.

The **confirmed** platform compatibility blocker precedes those checks on Android 6–12: installed-app discovery uses API-33 typed flags without a legacy branch, while version/signing inspection uses API-28 members despite the API-23 application floor.

The **confirmed** five-minute password timestamp applies only to blacklist editing and uninstall confirmation. `accessGranted` remains true for the ViewModel lifetime, leaving refresh and all update operations authorized indefinitely.

Blacklist state is a presentation filter and one-time `updateAll` snapshot, not an operation-time policy. This **confirmed** semantic gap allows an app blacklisted during a batch to update later in that same batch; the feature needs an explicit “hide” versus “must not manage” contract.

No new path intentionally clears Device Owner, Always-On VPN, firewall selection/rules, or kiosk state. A Bloq owns the VPN and is excluded, protected packages are rechecked before uninstall, and target firewall records are not deleted.

<summary>Issues (8)</summary>

1. **Supported-Android API mismatch — confirmed** — API-33 typed package flags and API-28 version/signing members are unguarded even though the app supports API 23. Add SDK-gated `Int` flag, `versionCode`, `signatures`, and `GET_SIGNATURES` paths, then verify catalog crypto across the supported API matrix.
2. **Installed-only commit race — confirmed** — the target can be uninstalled after the final installed/signing check, after which `MODE_FULL_INSTALL` installs the catalog APK as a new app. Hold an uninstall block across validation and commit or use a platform-enforced conditional update, then reconcile final package identity/version.
3. **Non-expiring update session — confirmed** — five-minute expiry gates only blacklist and uninstall; refresh/update/update-all continue while `accessGranted` stays true. Revoke access on timeout/background and enforce one session predicate at every privileged operation.
4. **Concurrent catalog rollback window — confirmed** — refresh is enabled while loading and results are unsequenced, so an older request can publish after a newer accepted revision and remain installable. Serialize fetch/accept/publication or reject stale results both at state publication and operation time; bind equal revisions to the same payload digest.
5. **Restorable rollback floor — confirmed** — the highest revision is stored in backed-up SharedPreferences while backup rules exclude only the database. Exclude anti-rollback state from backup/device transfer or use device-bound monotonic storage, and persist it durably before exposing catalog entries.
6. **Presentation-only blacklist — confirmed** — blacklist membership is not checked by update, uninstall, or the package operator. If it is an exclusion policy, enforce it at operation time and prevent or re-evaluate edits during a running batch; otherwise rename it as a display filter.
7. **Ephemeral installer completion — confirmed** — installer waits have no timeout or process-death recovery, and `STATUS_PENDING_USER_ACTION` is treated as a terminal generic failure. Add bounded waiting and durable session/package reconciliation, explicitly rejecting and cleaning up pending-user-action outcomes in the silent-only flow.
8. **Security boundaries untested — confirmed** — no tests cover catalog rollback, installed-only races, APK identity/integrity/lineage, installer statuses, password expiry, blacklist enforcement, or protected uninstall/state preservation. Add focused JVM/instrumentation coverage and an API-level matrix before shipping.

## Supported devices cannot execute the package trust path

**Confirmed:** `MiniStoreRepository.kt:77-78,94-96` calls the API-33 `ApplicationInfoFlags.of` and `PackageInfoFlags.of` overloads without checking `SDK_INT`. If execution reaches mapping, `MiniStoreRepository.kt:37,43-44` calls API-28 `PackageInfo.longVersionCode`. The operator repeats that assumption at `MiniStorePackageOperator.kt:45,53,56`, dereferences API-28 `PackageInfo.signingInfo` at `MiniStorePackageOperator.kt:198-202`, and passes API-28 `GET_SIGNING_CERTIFICATES` in its nominal legacy branches at `MiniStorePackageOperator.kt:217-233`. The application declares `minSdk = 23` at `app/build.gradle.kts:15`.

Android 6–12 can fail before rows render, and Android 6–8 cannot execute the version/signing checks even after the typed-flags call is fixed. Add the legacy package-manager branches already used elsewhere in the app and run the Ed25519/catalog path on every supported API family.

## Full-install sessions do not preserve installed-app-only atomically

**Confirmed:** installation is checked before download and immediately before session creation at `MiniStorePackageOperator.kt:43-59`. The operator then creates `SessionParams(MODE_FULL_INSTALL)` and commits later at `MiniStorePackageOperator.kt:127-143`, with no uninstall block or conditional-replace guard spanning the interval.

Removal after line 55 and before line 142 leaves PackageInstaller a valid full install for an absent package. Every content and signer check still passes, but the result violates the installed-only contract. Another pre-commit lookup only narrows the race; Device Owner policy should prevent removal for the operation’s duration or the install mechanism must atomically require an existing target.

## Entry authentication outlives its five-minute session

**Confirmed:** successful verification sets `privilegedUntil` at `MiniStoreViewModel.kt:62-63`, but only blacklist and uninstall consult it at `MiniStoreViewModel.kt:97-103,144-152`. Entry permanently sets `accessGranted` for the ViewModel at `MiniStoreViewModel.kt:171-174`; refresh and update paths at `MiniStoreViewModel.kt:82-92,112-139` do not revoke or consistently check session validity.

Leaving the destination on the back stack or backgrounding the app allows silent updates after the nominal five-minute expiry. Use one authorization predicate for every package operation and clear authorization and pending sensitive state on timeout/background. The settings copy should also clarify whether disabling the entry-password toggle intentionally retains step-up authentication for blacklist and uninstall.

## Revision acceptance can publish an older result after a newer one

**Confirmed:** refresh remains enabled during loading at `MiniStoreScreen.kt:57-59`, and each call starts an independent coroutine at `MiniStoreViewModel.kt:81-92`. The client checks and records the floor before returning at `MiniStoreCatalogClient.kt:50-53`, while UI publication happens later in the refresh coroutine.

A lower revision can pass first, pause before publication, then overwrite state after a higher revision has been accepted and displayed. `update()` consumes that stale model without rechecking the floor. Serialize the full fetch-to-publication transaction or generation-check publication and package operations. Because line 51 permits equality without storing a payload digest, separately signed payloads with the same revision are also interchangeable; equal revisions should require the already-accepted digest.

## SharedPreferences restore can lower the anti-rollback floor

**Confirmed:** `MiniStorePreferences.kt:23-29` stores the highest revision through asynchronous `SharedPreferences.apply()` at `PreferencesManager.kt:18-19,43`. Backup is enabled at `AndroidManifest.xml:27-31`, while `backup_rules.xml:3-8` and `data_extraction_rules.xml:4-15` exclude only Room files.

A reinstall or device transfer can restore an older floor, and a process failure can occur before an asynchronous write reaches disk. Either case permits an older validly signed catalog. Anti-rollback state must not be restored to a lower value and must be durable before its catalog becomes actionable.

## Blacklist changes do not authorize package operations

**Confirmed:** blacklist membership filters `visibleApps` and creates the batch once at `MiniStoreViewModel.kt:32-33,127-133`. `update()` forwards a captured entry without a current blacklist check at `MiniStoreViewModel.kt:112-123`; uninstall and `MiniStorePackageOperator` do not check it either. The editor action remains available during package operations at `MiniStoreScreen.kt:54-57`.

Blacklisting a not-yet-processed app during `updateAll` does not remove it from the captured batch. If blacklist means exclusion, check it immediately before every update/uninstall and freeze or re-evaluate a running batch. If it only hides rows, the current name overstates its security semantics.

## Silent PackageInstaller results are process-local and unbounded

**Confirmed:** `awaitInstallerResult` uses only a runtime receiver and suspended continuation at `MiniStorePackageOperator.kt:150-193`. There is no timeout, persisted session ID, startup reconciliation, or package-state fallback. Process death loses the receiver while PackageInstaller may finish, and a missing callback leaves the operation busy indefinitely. Lines 163-170 also collapse every non-success value, including intermediate `STATUS_PENDING_USER_ACTION`, into one terminal failure.

The silent Device Owner flow should bound waiting, record enough operation/session identity to reconcile after restart, distinguish terminal failure from pending user action, and explicitly abandon or reconcile work that unexpectedly requires UI.

## Trust and lifecycle boundaries have no regression suite

**Confirmed:** repository search found no unit or instrumentation references to the mini-store, catalog client, package operator, or blacklist behavior, and the site’s `package.json` test script exits with “no test specified.” Coverage is needed around signature/revision rejection, APK validation, package removal before commit, installer completion/recovery, password lifecycle, blacklist races, protected uninstall, and policy-state preservation.

No build or test command was run because the request prohibited file modifications and Gradle/Node tasks would write build or generated catalog artifacts. Inspection covered both uncommitted sets, all untracked implementation files, prior reviews, and surrounding package/VPN/update/backup code.
